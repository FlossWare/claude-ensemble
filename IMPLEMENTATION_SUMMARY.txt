CACHE INVALIDATION MECHANISM
================================================================================

How Cache Invalidation Works:

AUTOMATIC (Content-Based)
  When: File content, block count, or filename changes
  How: Content hash in key changes → old cache invalid
  
  Examples:
    - Edit CLAUDE.md → content hash changes → new key
    - Add new memory file → block count changes → new key
    - Rename file → path in key changes → new key
    - Delete file → block count changes → new key

VERSION-BASED (Format Change)
  When: CACHE_FORMAT_VERSION incremented
  How: Version in key changes → all old cache invalid
  Use: Breaking changes to cache structure
  
  Examples:
    - Change from "1.0" to "1.1" → all cache invalid
    - Migrate to new hash algorithm → increment version
    - Change cache schema → increment version

BLOCK-LEVEL (Selective Caching)
  When: Include/exclude blocks from cache
  How: Different blocks → different key
  Use: Optimize cache size vs coverage
  
  Examples:
    - Cache only critical files → smaller key
    - Exclude rarely-changing docs → faster hashing
    - Different configs → different keys

No Manual Invalidation Needed:
  - Content changes automatically invalidate cache
  - File system drives cache validity
  - Transparent to users
  - Self-healing

HOW IT WORKS (Algorithm Details)
================================================================================

Cache Key Generation Algorithm:

  Step 1: Input Validation
    - Accept list of CacheableContent blocks
    - Verify all content is present
    - Check for empty input

  Step 2: Block Sorting
    - Sort by file path for deterministic ordering
    - Ensure block order doesn't affect key
    - Prevents accidental key differences

  Step 3: Individual Block Hashing
    - Hash each block's content with SHA256
    - Encode content as UTF-8
    - Store hash in metadata

  Step 4: Composite Creation
    - Create string: path|type|hash for each block
    - Format: "/path/file.md|system_prompt|abc123..."
    - Do this for all blocks

  Step 5: Format Version Inclusion
    - Prepend "FORMAT:1.0" to composition
    - Enables future cache invalidation
    - Versioning without recomputation

  Step 6: Combination
    - Combine all components with | separator
    - "FORMAT:1.0|path1|type1|hash1|path2|type2|hash2|..."

  Step 7: Final Hash
    - Hash the combined string again
    - SHA256 of the entire composition
    - Return hex digest

  Result: Single deterministic 64-character hex string

Determinism Properties:
  - No randomness anywhere in algorithm
  - No timestamps or external state
  - UTF-8 encoding ensures platform consistency
  - Same input → same output, always

Collision Resistance:
  - SHA256: 2^256 possible values
  - Practically impossible: different content → different key
  - Tested: verified with multiple modifications
