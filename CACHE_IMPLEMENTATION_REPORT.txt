CACHE INVALIDATION MECHANISM
================================================================================

AUTOMATIC INVALIDATION (Content-Based)

When cache key changes:
  1. File Content Modified
     - Edit CLAUDE.md → content hash changes → key differs
     - Old cache automatically invalid
     - Next generation uses new key

  2. Files Added/Removed
     - Add new memory file → block count changes → key differs
     - Old cache automatically invalid
     - Sorting ensures order independence

  3. File Renamed
     - Rename file → path in key changes → key differs
     - Old cache automatically invalid

VERSION-BASED INVALIDATION

When format changes:
  - Increment CACHE_FORMAT_VERSION (currently "1.0")
  - ALL existing cache becomes invalid
  - Use for breaking changes to cache structure
  - Old clients can't use new cache format

BLOCK-LEVEL CONTROL

Selectively cache content:
  - Include only critical blocks for smaller keys
  - Exclude rarely-changing files for faster hashing
  - Flexibility for different cache strategies

================================================================================
HOW IT WORKS
================================================================================

Algorithm:
  1. Sort content blocks by file path (deterministic ordering)
  2. Add format version (enables cache versioning)
  3. Hash each block's content with SHA256
  4. Create composite: path|type|hash for each block
  5. Combine all with | separator
  6. Hash the combined string again (final cache key)

Determinism:
  - UTF-8 encoding ensures cross-platform consistency
  - No timestamps or randomness included
  - Same input → same output, always

Collision Resistance:
  - SHA256: 2^256 possible values
  - Practical: Different content produces different keys 100% of the time
  - Two different files will never produce same cache key
