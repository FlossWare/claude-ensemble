HOW IT WORKS (30-SECOND OVERVIEW)
================================================================================

PHASE 1: DISCOVERY
└─ Analyze execution history (execution_log table)
   └─ Identify 7 types of learning opportunities:
      1. Knowledge gaps (high uncertainty decisions)
      2. High variance (unstable outcomes)
      3. Underexplored space (few samples)
      4. Untested combinations (never tested together)
      5. Divergent performance (models disagree)
      6. Low confidence (arbiter uncertain)
      7. Cost anomalies (unexpectedly expensive)
   └─ Score each opportunity by:
      - Impact: How important? (0-100)
      - Cost: How expensive? (0-100)
      - Efficiency: Impact/Cost (ROI)
   └─ Output: Top 20 opportunities sorted by efficiency

PHASE 2: PLANNING
└─ Group opportunities into learning campaigns
└─ Build experiment priority queue
└─ Allocate token budget across experiments
└─ Generate executable experiment prompts
└─ Define success criteria for each experiment
└─ Output: Strategic learning plan with experiment queue

PHASE 3: EXECUTION
└─ Run experiments in priority order
└─ Collect specified metrics (quality, cost, confidence, etc.)
└─ Validate outcomes against success criteria
└─ Store results in execution_log database
└─ Provide real-time feedback

PHASE 4: FEEDBACK
└─ Analyze experiment outcomes
└─ Generate learning report
└─ Provide recommendations
└─ Suggest next experiments
└─ Close the loop (go back to Phase 1 with new data)

  └─ Impact: 7-11 point quality improvement

  └─ Discover: Never tested [gpt-4o, opus] together

  └─ Result: Quality 0.87, cost $0.15
  └─ Decision: Add to standard high-quality combinations
  └─ Impact: New capability unlocked for critical tasks

================================================================================
OPPORTUNITY TYPES EXPLAINED
================================================================================

KNOWLEDGE GAPS (I: 50-100, C: 5-15)
└─ What: Decisions made with high uncertainty
└─ When: High variance in outcomes for similar tasks
└─ Example: "Which model for code-review? Varies widely"
└─ Fix: Run direct comparison, measure quality consistently

HIGH VARIANCE (I: 40-100, C: 4-10)
└─ What: Task/model combos with unstable results
└─ When: Standard deviation > 0.15 across executions
└─ Example: "Model X sometimes 90%, sometimes 70% on same task"
└─ Fix: Identify confounding variables, stratify by them

UNDEREXPLORED SPACE (I: 20-60, C: 1-5)
└─ What: Parameter combos with very few samples
└─ When: Model combo tried < 3 times
└─ Example: "[opus+haiku] never tested together"
└─ Fix: Run a few experiments, validate/reject combo

UNTESTED COMBINATIONS (I: 40-80, C: 3-8)
└─ What: High-potential pairs never tested
└─ When: Theoretical best combos haven't been tried
└─ Example: "Never tried [gpt-4o, opus] despite both being strong"
└─ Fix: Run 3 representative tasks, measure quality

DIVERGENT PERFORMANCE (I: 50-100, C: 6-12)
└─ What: Models strongly disagree on task quality
└─ When: Quality gap between best/worst model > 20%
└─ Example: "Opus 85% vs Sonnet 65% on code-review"
└─ Fix: Run blind comparison, get user ratings, understand why

LOW CONFIDENCE (I: 20-60, C: 2-5)
└─ What: Arbiter uncertain about decisions
└─ When: Confidence score < 70% on common tasks
└─ Example: "Arbiter picks model but isn't confident"
└─ Fix: Collect user feedback, recalibrate confidence

COST ANOMALIES (I: 30-80, C: 1-4)
└─ What: Unexpectedly expensive models
└─ When: Cost-per-quality > $1.00
└─ Example: "Haiku costs 10x more than Sonnet for same quality"
└─ Fix: Compare to alternatives, replace if viable

TECHNICAL ARCHITECTURE
================================================================================

INPUT: SQLite Database
├─ execution_log: Records of every workflow execution
│  └─ workflow, task_type, quality_score, total_cost_usd, worker_models, etc.
├─ model_performance: Aggregated metrics per model
│  └─ avg_quality, cost_per_quality, selection_rate, sample_count, etc.
└─ parameter_tuning: Optimal parameters discovered
   └─ model, task_type, optimal_params, avg_quality, confidence, etc.

PROCESSING PIPELINE:
1. active-learning-engine.js
   └─ Run 7 detection strategies in parallel
   └─ Score opportunities by impact/cost
   └─ Sort by efficiency
   
2. strategic-learning-planner.js
   └─ Organize into campaigns
   └─ Build priority queue
   └─ Allocate budgets
   
3. experiment-executor.js
   └─ Execute experiments
   └─ Validate outcomes
   └─ Store in database

OUTPUT: Updated Database + Reports
├─ New execution_log records (experiment outcomes)
├─ New quality_ratings records (validation results)
├─ Updated model_performance table
└─ Markdown/JSON reports

├─ underexplored_space: enabled, max_samples=3
├─ untested_combinations: enabled, base_impact=60
├─ divergent_performance: enabled, threshold=0.2
├─ low_confidence: enabled, threshold=0.7
└─ cost_anomalies: enabled, threshold=$1.00

MONITORING & SUCCESS METRICS
================================================================================

TRACK EFFECTIVENESS:

1. OPPORTUNITY QUALITY
   └─ Metric: Post-experiment quality vs baseline
   └─ Target: ≥ 5% improvement
   └─ Question: Did identified opportunities actually matter?

2. PREDICTION ACCURACY
   └─ Metric: Estimated vs actual tokens/time
   └─ Target: < 20% error
   └─ Question: Are our cost estimates accurate?

3. ROI (Return on Investment)
   └─ Metric: Actual learning value / predicted value
   └─ Target: > 0.8
   └─ Question: Do high-efficiency opportunities deliver value?

4. CONVERGENCE
   └─ Metric: Model consensus trend (50 recent executions)
   └─ Target: ≥ 0.8 average
   └─ Question: Are models converging on similar decisions?

5. COVERAGE
   └─ Metric: % of important decision points explored
   └─ Target: ≥ 80%
   └─ Question: Are we learning about all critical areas?
